Update Logs

November 12, 2026

Encrypting Secrets at Rest: While setting up the VPN, I took a closer look at where the lab's secrets actually lived, and didn't like the answer. VPN credentials, the tunnel key and API keys sat in plain-text .env files, and the nightly backup job was faithfully copying them to the second disk every day, with 30 days of retention. Fifteen copies of every secret, in plain text, in a backup folder.

The Fix: Every secret now lives in a file encrypted with sops and age, and is decrypted only in memory at the moment a container is created. Compose files were changed to refuse to start if a secret is missing, so the old plain-text path can't be used by accident. The private key is kept out of the backups entirely and stored separately in a password manager, so a stolen backup is useless on its own. I evaluated Proton Pass's CLI first, which offers nicely scoped read-only tokens, but it required a higher plan tier, and sops + age turned out to be free, offline and an industry-standard pattern.

Verifying Without Looking: Each secret was checked after encryption by comparing its length, or a hash prefix against the value the running container was using, without ever displaying it. After the containers were recreated and re-tested, every plain-text copy was shredded, including all fifteen backup snapshots, and a final search across the server and backup disk found no plain-text copies left.

Honest Limits: This protects files, backups and accidental leaks, not a fully compromised host, since root can still read a running container's environment. Overwriting files on a journaling filesystem is also best-effort, so the complete fix for a truly sensitive key is to rotate it.

November 12, 2026

Private File Sharing Behind a VPN Kill Switch: To share large files with friends, I deployed qBittorrent with every byte of its traffic forced through a commercial VPN. The client runs inside the network namespace of a gluetun container, so it has no network interface of its own. Its only route to the internet is an OpenVPN tunnel, and gluetun's iptables firewall drops all outbound traffic that doesn't use that tunnel. As a second layer, qBittorrent itself is bound to the tun0 interface, and UPnP is disabled so no application can open router ports on its own.

Trust, but Verify: Rather than assume the kill switch worked, I tested it. Peers see the VPN provider's address, not my ISP's; DNS queries resolve through gluetun's own resolver; and when I killed the OpenVPN process mid-session, qBittorrent could no longer reach the internet by hostname or raw IP until the tunnel reconnected on its own. The first test attempt silently failed to kill the process, which would have produced a false "leak" result. Checking the test itself before trusting the outcome was a lesson in its own right.

Four Bugs, One Tunnel: Getting connected meant working through four separate faults: an outdated server list (fixed with gluetun's updater), UDP port 53 being intercepted on the home network (switched to TCP), website credentials used in place of the VPN-specific credentials, and a $ in the password that Docker Compose was interpolating as a variable, silently truncating it from 12 characters to 2. That last one was found by comparing the secret's length in the file against what the container received, without ever printing it.

November 12, 2026

Incident: Hardening vs. GPU Workloads: After the first reboot since the October hardening pass, both GPU containers (Jellyfin and Ollama) refused to start with nvidia-container-cli: mount error: failed to add device rules. A throwaway test container failed the same way, which ruled out a problem with either application and pointed at the GPU runtime itself.

Finding the Root Cause: Two changes had landed since the containers last started: a kernel update and a set of kernel hardening sysctls. Rather than guess, I wrote a diagnostic script that tested each theory in isolation and changed nothing permanently. The culprit was net.core.bpf_jit_harden = 2. The NVIDIA Container Toolkit's legacy mode builds an eBPF cgroup filter for every GPU container, and the stricter setting causes that program to be rejected. With the value temporarily set to 0, the GPU came straight back.

The Trade-Off: The quick fix would have been to lower the setting and move on, quietly weakening the host to make a feature work. Instead, the containers were migrated to CDI (Container Device Interface) mode, NVIDIA's newer method that passes the GPU as a named device without building that filter. The hardening stays at full strength, the GPU works, and a systemd unit regenerates the device spec automatically after driver updates.

Lesson Learned: Hardening changes don't always break things immediately. This one sat dormant for two weeks until the next reboot. Going forward, hardening changes get a reboot test straight away, and every security setting that is relaxed has to be justified.

November 12, 2026

Game Server Deployment & Zero-Exposure Networking: The first production workload is live: a modded Minecraft server (Create Ultimate Selection on NeoForge 1.21.1) shared with a friend. The server was migrated from a plain Docker image to Crafty Controller, which provides a web panel, role-based accounts, scheduled backups and twice-daily restarts with in-game warnings. Because the lab sits behind double NAT (NBN modem into a second home router over powerline), traditional port forwarding was never a clean option, and opening ports would have exposed the host directly to the internet anyway.

Tunnels Instead of Open Ports: Public players connect through a playit.gg agent container, which holds an outbound tunnel to playit's edge and relays game traffic back to the server on 127.0.0.1. Nothing on the router is forwarded. Administrative access uses Tailscale, a WireGuard-based mesh VPN: every Docker service (Crafty panel, game port, Open WebUI) is bound to localhost only and then published to my private tailnet with tailscale serve. The LAN itself can no longer reach those services, which was verified from another machine. The result is a single, deliberate internet entry point for the game and an encrypted, identity-based path for everything else.

Host Hardening: SSH moved to key-only authentication with root login disabled, a single allowed user and limited auth attempts. ufw now defaults to deny inbound, allowing only the tailnet, Tailscale's UDP port and SSH from the local subnet, with fail2ban watching SSH. Kernel sysctl hardening was applied and unused network protocols (DCCP, SCTP, RDS, TIPC) were blacklisted. A Lynis audit moved the hardening index from 66 to 71 with zero warnings.

Secret Scanning for Public Docs: With the documentation now published straight from the server, a leak is one commit away. Every commit is scanned by gitleaks in a pre-commit hook, which blocks anything that looks like an API key, token or private key. On top of the built-in rules, custom rules catch homelab-specific details such as internal hostnames, private IP addresses and tunnel addresses. Those custom rules are deliberately kept outside the public repository, because a rules file listing what to hide would itself reveal it. The hook was tested with a planted fake address, and the full commit history was scanned clean.

Backup Strategy: Crafty takes world backups every six hours, and an hourly cron job copies the newest archive from the NVMe to the 2TB HDD with a rolling retention policy, so a single drive failure no longer means losing the world.

CTF Lab Phase 1: Built an isolated libvirt network (10.66.0.0/24, no forwarding) with separate storage pools for VM disks and checksum-verified base images. A self-destructing Alpine test VM attempts to reach the host, LAN, router, tailnet and internet; all 19 checks were blocked. Attack VMs will move onto the server after the RAM upgrade.

Shifting Focus to Networking: Going forward, I am steering this lab toward networking skills. Upcoming work covers self-hosted DNS with Pi-hole and Unbound, Wake-on-LAN, monitoring with Prometheus and Grafana, and ultimately a full VLAN segmentation of the home network behind an OPNsense firewall. The updated plan is in the roadmap above and in the documentation repository.

May 28, 2026

Hardware Pivot & Lifecycle Extension: Repurposing an NVIDIA RTX 3070 Ti for the server build. The card began exhibiting instability under heavy 3D rendering loads in a primary workstation. However, by aggressively undervolting and power-limiting the card, it will remain perfectly stable for hardware media transcoding. This works because media encoding relies entirely on the dedicated NVENC silicon rather than raw CUDA compute power, extending the usable life of the hardware.

May 28, 2026

Architecture Decision - Proxmox VE: Evaluated bare-metal hypervisor options for the host OS. Selected Proxmox VE (built on Debian Linux) over VMware ESXi due to licensing changes and hardware compatibility constraints with consumer-grade motherboards. Proxmox will allow for an efficient resource footprint using lightweight Linux Containers (LXC) for services like Pi-hole, maximizing the utility of the lab's 16GB RAM budget while providing native support for PCIe pass-through of the RTX 3070 Ti.
